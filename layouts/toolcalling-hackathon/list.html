01

The challenge

Overview

AI assistants are moving beyond answering questions. Instead of telling you how to buy airtime, an assistant can buy the airtime for you. Instead of explaining how to send money, it can send the money.

To do this, an assistant needs to use tools. A tool is a function that lets an AI system take an action or look up information, such as send_money(recipient, amount, currency, provider). The model has to work out which tool to use and what information to give it.

In this hackathon, you will train a small language model that takes an everyday request from across Africa, looks at the tools available to it, and produces the correct tool call.

Request

“Abeg send 5k naira to Tunde on MTN MoMo.”

Available tools

  • send_money
  • check_balance
  • buy_airtime
  • convert_currency

Correct tool call

{
  "tool": "send_money",
  "parameters": {
    "recipient": "Tunde",
    "amount": 5000,
    "currency": "NGN",
    "provider": "MTN MoMo"
  }
}

That's the entire challenge

Given a request and a set of tools, make the correct tool call.

Why small language models?

Large language models can be very capable at tool use, but they are expensive and difficult to run in resource-constrained environments. This hackathon asks a different question: how capable can a small language model become when we train it specifically for tool calling?

You will work with open models of up to 4 billion parameters and experiment with fine-tuning, synthetic data generation, prompting and inference strategies. The goal is not to build the biggest model. The goal is to build the most accurate small one.

Individuals and teams

You may take part on your own or as a team. Each participant or team submits through one Codabench account.

The dataset maps English-language requests in African contexts to the right tool and its parameters. Each example has a request, 4 to 6 available tools (the relevant ones and some distractors), and the answer.

How the splits work

Train 15,000 examples
Request, tools and answer. Use it to train and validate your model.
Dev 2,000 examples
Request and tools, with the answers hidden. Submit predictions to see your score on the development leaderboard.
Test 4,000 examples
Request and tools, with the answers hidden. Released when the final phase opens, and used for the final ranking.

The dev and test sets use different names, neighbourhoods, towns, markets and wording from the training data. The aim is to test whether your model has learned tool calling rather than memorised examples.

Starting points

Baselines

Out of the box, small models are poor at this task. Without training, Gemma 3 270M gets almost no requests right, and even Gemma 3 4B gets about a third (34% on a 300-request sample of dev). Fine-tuning changes that.

Baseline scores to beat (exact-match accuracy on dev)
BaselineDev score
Hand-written rules, no model49.05%
Gemma 3 270M, fine-tuned on 3,000 examples64.55%
FunctionGemma 270M, fine-tuned on 3,000 examples77.00%
Gemma 3 270M, fine-tuned on all 15,000 examples88.35%

Even the smallest Gemma model goes from almost nothing to 88% with fine-tuning. How close to 100% can you get?

What might you explore?

  • FunctionGemma 270M
  • Larger models, up to 4B
  • LoRA / QLoRA

  • Hard-example mining
  • Data curation
  • Knowledge distillation
  • Few-shot prompting
  • Self-consistency
  • Test-time scaling
  • Ensembling

Try these, combine them, or develop your own idea. Try, evaluate, improve, repeat.

05

How scoring works

Evaluation

There is one metric. A prediction is correct only when the selected tool and all of its parameters match the answer. When a request needs several calls, every call must be correct and in the correct order.

The metric

Exact-match accuracy

Accuracy=completely correct predictionstotal predictions
3,400 correct÷4,000 requests=85%

Higher is better.

What counts as wrong

If the answer is send_money to Tunde for 5000 NGN on MTN MoMo, then each of these predictions is wrong:

  • The right tool, but amount: 500.
  • The right tool and amount, but the wrong provider.
  • A value that is not in the request, such as a provider the user never mentioned.

How answers are compared

  • Text ignores case, punctuation and extra spaces, so "m-pesa" matches "M-Pesa".
  • Numbers are compared as numbers: 5000 matches 5000.0, but the text "5000" does not.
  • A parameter left out counts as null.
  • A list containing one call is the same as that call.

Keep this in mind

A model should never invent information that is not in the request. If a value is missing, it is null.

From idea to entry

How to submit

The hackathon runs on Codabench. You upload a ZIP file with your predictions, and your score appears on the leaderboard once it has been scored.

Rules

  • Use any open-weight model with at most 4B parameters. Gemma 3 270M, 1B and 4B, and FunctionGemma 270M are recommended.
  • No API calls or larger models may be used when generating predictions.
  • Any training technique is allowed, including fine-tuning, synthetic data generation, prompting and decoding strategies.
  • You may augment the training data.
  • You may not manually label development or test examples.

Good to know

Frequently asked questions

Do I need my own GPU?

No. The starter notebook fine-tunes Gemma 3 270M on a free Google Colab GPU.

Which models can I use?

Any open-weight model with at most 4 billion parameters. Gemma 3 270M, 1B and 4B, and FunctionGemma 270M are recommended.

Can I use ChatGPT, Gemini or another large model?

Not to make your predictions: no API calls or larger models may be used when generating predictions. Any training technique is allowed, including synthetic data generation.

Can I add my own training data?

Yes. You may augment the training data, for example with synthetic examples. You may not label development or test examples by hand. The meta field in train.jsonl describes each example (category, country, style and more) to help you generate data of your own.

What language are the requests in?

English, set in everyday life across Africa, with local expressions and chat shorthand such as “Abeg” or “500 bob”.

What if a request does not give a value the tool needs?

That value is null. For example, “Send 2,000 naira to Tunde.” does not name a provider, so provider is null. A model should never invent information that is not in the request.

What if a request needs several actions?

Return a list of tool calls, in the order the request asks for them. Every call must be correct for the prediction to count.

Why is my dev score lower than my validation score?

The dev and test sets use names, places and wording that are not in the training data. A validation split taken from train.jsonl shares them, so it is more optimistic. The dev leaderboard is the better guide to your test score.

What should my submission look like?

A ZIP file with predictions.json at its top level. The file maps every request id to its tool call, or to a list of calls. Ids that are missing count as wrong.

My submission failed. What should I check?

Check that predictions.json is valid JSON, that it is a single object keyed by request id, and that it is inside the ZIP you uploaded. The error message on your Codabench submission says what went wrong.

How many times can I submit?

Up to 5 times a day (100 in total) in the development phase, and up to 2 times a day (5 in total) in the final phase. The leaderboard shows your best score.

Which score decides the winner?

Exact-match accuracy on the test set, in the final phase. The development leaderboard is for testing your ideas.
